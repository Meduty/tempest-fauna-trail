# T.14 — Save / Load (JSON Run persistence)

**Date:** 2026-06-05
**Task:** SPEC §T.14 — `game/save.py`. Status ❌ → ✅.

## What shipped

`src/game/save.py` — the **file-I/O layer** over the model (de)serialization
contract (which already lived on the dataclasses since T.1, fully tested). New
surface only:

- `save_run(run, path)` — atomic write: temp `<path>.tmp` → `flush`+`fsync` →
  `os.replace`; auto-mkdir parent; temp removed on any failure.
- `load_run(path)` — `schema_version` gate → `Run.from_dict`. Typed errors.
- `CURRENT_SCHEMA_VERSION = 1` — first central home (was hardcoded at 4 test
  sites); also the in-`load_run` migration hook point.
- `default_save_dir()` — platform app-data resolver (`%APPDATA%` / macOS
  `Application Support` / `$XDG_DATA_HOME`), no new dep. Helper only; core fns
  take explicit paths.
- `SaveError` → `CorruptSaveError`, `UnsupportedSchemaError`.

`tests/game/test_save.py` (9 cases, 18 with parametrize) — green; full suite
698 passed / 101 skipped. New invariant **V.36**. Living docs updated
(`save.md` flipped its "planned file I/O" row to built; ARCHITECTURE got a
`save.py` entry).

## Why the decisions

- **Minimal path API, not a slot manager.** T.9 (menu) / T.10 (run-start) are
  unbuilt — there is *no* consumer for named slots / `list_saves` / autosave
  yet. Building it now = speculative API. Deferred to T.9 along the real seam.
- **Persist full `battle_log`.** Keeps the round-trip-identity invariant exactly
  as `save.md` states. Bloat is hypothetical; trimming would force a §V
  amendment for no proven gain.
- **Atomic + typed + schema gate.** Cheap robustness that sets the migration
  seam. A save you can't load is worse than no save.

## Process notes (AI collaboration)

- **CLAUDE.md vs SPEC conflict — "no I/O in game logic".** CLAUDE.md's
  Game-State section says *"No I/O in game logic — API/file access stays in
  api/ layer"*, but SPEC §T.14 names the module `game/save.py`. Resolved in
  SPEC's favor: the actual invariant **V.1 bans only Flet imports**, not file
  I/O — the CLAUDE.md line is a looser convention. V.36 now states the I/O home
  explicitly so the conflict is documented, not just resolved in my head. This
  is the kind of doc-vs-doc drift the required-reading step is meant to catch;
  it did.
- **The task was 80% already done and the plan caught it.** Required reading
  (`save.md` + `models.py`) revealed the entire (de)serialization contract +
  B.4 back-compat already existed and was tested. Without that read I'd have
  re-implemented `to_dict`/`from_dict` and probably drifted the contract. The
  plan's "gap today" table is what kept scope to *just* the I/O wrapper.
- **Self-review caught a real correctness hole before any code.** First plan
  draft wrapped only `JSONDecodeError`/`KeyError` → `CorruptSaveError`. The
  review pass (grepping `models.py`) found `__post_init__` validators and
  `_parse_enum` raise plain **`ValueError`** — a semantically-broken-but-
  JSON-valid save would have escaped as a raw `ValueError`, breaking the typed
  contract. Patched plan to catch `(KeyError, ValueError, TypeError)` and added
  a dedicated test (`tempest_rank=11`, bad enum). Cheaper to find in the plan
  than in a bug report.
- **`bool` is an `int` trap.** `isinstance(True, int)` is `True` in Python, so
  the schema-version type guard explicitly excludes `bool` — otherwise a
  `schema_version: true` payload would sail through the gate. Covered by the
  parametrized type test.
- **No backprop needed** — tests passed first run; no §B entry (V.36 is a
  forward guard, not a bug fix).

## Prompting-strategy reflection

- **Plan → review → build as three separate user turns worked well.** The user
  explicitly asked me to *review my own plan* before building. That forced a
  second adversarial pass over my own work (grep the error types, not trust the
  prose) which is exactly where the `ValueError` gap surfaced. Self-review as a
  distinct step — not folded into planning — earns its keep.
- **`AskUserQuestion` with "Recommended" first + concrete trade-offs** got all
  four scope forks resolved in one round with zero back-and-forth. The forks
  were genuine (slot-manager scope, save location, battle_log bloat,
  robustness depth), each changing the deliverable — not preference noise. Good
  fit for the tool; would have been wrong to just pick defaults silently given
  the battle_log-bloat one touches an invariant.
- **Skill chaining (`/build` → `/check` → `/spec`) kept the guardrails honest.**
  Build flips status only; `/check` confirmed every cited symbol resolved and
  flagged V.36 as forward-referenced-but-missing; `/spec` then landed it. The
  "living doc cites an invariant that doesn't exist yet" was caught by the
  audit, not by me remembering — which is the point of running `/check` even on
  a task I was confident in.
