# 2026-06-25 — T.23a: Prep view (full economy, no items)

## Overview

Built the Prep view (`ui/views/prep.py`, route `/prep`) — the pre-combat decision
layer that closes the Trail→Prep→Combat seam. Placement on a hex board (TFT-style
drag bench↔board within the allied deployment zone), the shop (buy/reroll/sell/
rank-up), deterministic enemy preview, and tap-to-inspect stat tooltips. Start-Combat
builds a `CombatSession(positions=team_positions)` shape-identical to the dev-harness
producer and hands it to the host.

The only engine-side residue: `game/loadout.py::validate_team_positions` +
`ALLIED_ZONE_MAX_Q = 3` — a team-only validated wrapper (zone + roster-id) layered on
top of the landed V.62 engine guard (V.68). Everything else is pure presentation over
the finished economy/shop/combat backend (V.63).

Items deferred to T.23b (split agreed with the user — items need a new `game/` equip
seam; the loop closes without them).

## What landed

- **`game/loadout.py`** — `ALLIED_ZONE_MAX_Q = 3`, `validate_team_positions(team,
  positions)`. Raises on off-zone (`q >= 3`), off-board row, dup cell, or an id not on
  the team. Empty positions (Auto-Place) passes.
- **`ui/components/board_geometry.py`** — extracted the hex pixel layout (`cell_xy`,
  `COL_W`, `ROW_H`, `BOARD_W/H`) from the combat view into one shared module. The combat
  view now imports it and aliases its old private names (`_cell_xy = cell_xy`, etc.) —
  byte-identical geometry, no second coordinate system to drift.
- **`ui/views/prep.py`** — the view. `run.roster` = deployable field (capped at
  `tempest_rank`), `run.bench` = reserves; drag moves a champion between the two lists.
  Auto-Place mirrors `engine.assign_spawns` packing (`i → (i//7, i%7)`) so it's
  byte-identical to `positions=None`.
- **`main.py`** — `_push_prep_stub` → `_push_prep` (real view + opens combat;
  `on_exit=lambda: _pop(page)` until T.15 wires the reward step).
- **Tests** — `tests/game/test_prep_positions.py` (9: validator + V.62 byte-identity
  regression), `tests/ui/test_prep.py` (3: construction + Start-Combat seam parity).
- **Docs** — `docs/live/systems/ui.md` Prep section + status flip; SPEC T.23a → ✅.

## Process notes (AI collaboration)

- **Deployment-zone drift caught in planning, not in code.** The MVP slice doc
  (`t10_mvp_run_loop_plan.md`) had proposed `q < BOARD_WIDTH//2` (= cols 0–4) for the
  allied zone — a loose "left half" first-pass guess. Grepping the docs during the focused
  T.23 plan surfaced `t24_enemy_formation_plan.md:56`: the **landed** T.24 formation
  actually pairs player cols 0–2 / enemy cols 7–9. The user independently recalled "3
  columns each side." So the real zone is `q < 3`, not `q < 5`. Fixed in the plan (§6) +
  pinned by **V.68** so the two numbers can't re-diverge. Lesson reinforced: *the frozen
  design doc that actually shipped beats the newer planning doc's unverified guess* — and
  the cheapest place to catch a constant-level drift is the plan's content↔design check.
- **`assign_spawns` packing had to be read, not assumed.** Auto-Place must be
  byte-identical to the default formation (V.62/V.2). I read `engine.assign_spawns`
  (`position_q = i // BOARD_HEIGHT`, `position_r = i % BOARD_HEIGHT`) rather than guess,
  then encoded the same packing + added a regression test that builds combat both ways and
  asserts equal team cells. Determinism guards stay green.
- **Two small API mismatches, both caught by the smoke test before handoff.**
  (a) `ft.border.all` → the real API is `ft.Border.all` (capital B) — the combat view
  already used it; I'd pattern-matched the lowercase form from memory. (b) `ctx.pieces` →
  the accessor is `ctx.all_pieces()`. Neither would've been caught by the pure-logic
  validator tests; the **view-construction smoke test** (`tests/ui/test_prep.py`, fake
  page) is what exercised the render path and flushed them out. Reaffirms the value of a
  headless construction test even for "untested" views.
- **Self-verify on `--web`, per the standing lesson (web ≠ desktop for thread→UI).**
  Rather than click-navigate menu→…→prep on a Flet canvas (flaky), I deep-linked a scratch
  app straight into `build_prep_view` and screenshotted it. Confirmed layout renders
  without crashing — the thing the smoke test can't see.
- **Scope discipline held.** The spec row says "engine residue = only
  `validate_team_positions` + the constant." Bench↔field is genuinely just moving
  `Champion` objects between two public `Run` lists (no economy number recomputed), so it
  stayed in the view per V.63 rather than growing a new `game/` helper — keeping 23a's
  engine surface to exactly what the plan promised.

## Prompting-strategy reflection

The winning move this slice was **front-loading a focused plan doc even though a
slice-level plan already existed.** `t10_mvp_run_loop_plan.md` "covered" T.23, but writing
the dedicated `t23_prep_view_plan.md` forced a per-seam verify pass that caught the
zone-constant drift and the items-equip-seam gap *before* any code — the gap turned into a
clean 23a/23b split (a real shippable seam) instead of a mid-build surprise. The
`AskUserQuestion` forks (items scope, deployment zone) were genuine: the user split items
out and confirmed the 3-column zone from memory, which matched the frozen T.24 doc. Asking
the two real forks up front, then resolving everything else with stated proposals, kept the
build a straight execution with zero back-and-forth. The pattern that keeps paying off:
**plan verifies against code → spec pins the invariant → build executes** — each stage's
output is the next stage's contract, so drift gets caught at the cheapest layer.
