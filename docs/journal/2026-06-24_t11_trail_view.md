## What landed

The between-fights hub, the first of the run-loop UI views built over the
finished backend:

- **`viz/route_map.py`** — graded Canvas viz, two layers (mirroring
  `ui/combat_playback.py`'s pure-model/view split): pure `route_node_specs(run,
  weather_for, selected_index)` (test-asserted structure) + `build_route_map(...)`
  drawing the 50-node line with `flet.canvas` and transparent overlay hit-test
  buttons.
- **`ui/views/trail.py`** — `build_trail_view`: node focus panel (weather favor
  tally + deterministic enemy preview), team summary, and a **Trail-owned live
  weather refresher** started on open / stopped on pop+Save&Exit (`view.data`
  handler, the same convention the combat view uses for its autoplay thread).
- **`game/encounter.py`** — new `node_encounter(run_seed, node, weather, dc) ->
  NodeEncounter` dispatcher: the **one** deterministic seam the Trail preview uses
  now and Prep's `Start Combat` will reuse (T.23), so previewed squad == fought
  squad byte-for-byte (V.2).
- **`game/route.py`** — `ROUTE_CITY_IDS` + `city_id_for_node(index)`: the `Node`
  only carries the city *name*, so the weather cache (keyed on city id) needed a
  route-order id mapping.
- **`api/refresher.py`** — back-compat optional `WeatherRefresher(on_tick=…)`
  callback so the UI can repaint when a cache entry flips LIVE/SUBSTITUTE, on the
  worker thread (V.4). Default `None` keeps every existing caller byte-identical.
- **`main.py`** — New Run → RunStart → `_push_trail`; Play Next → `_push_prep_stub`
  (placeholder until T.23); Save & Exit → `save.save_run` autosave (V.65) + pop.

Verified headless (full suite 1288 passed, 101 skipped) **and visually** —
served `--web` + Playwright screenshot of the Trail: route line with node 1
current (blue), node 10 boss (red ring), per-node weather labels, focus panel
(Lisbon / reward badge / favor 0↑3·0↓ / 2-enemy preview), team summary (Amber 14,

## Process notes (AI collaboration)

- **Method-vs-attribute name collision (caught by an existing test).** I added
  `self._on_tick = on_tick` to `WeatherRefresher` — but the class already had an
  `_on_tick` *method* (the timer callback). The instance attribute shadowed the
  method, so the timer armed `threading.Timer(interval, None)` → `TypeError:
  'NoneType' object is not callable` in the worker thread. The **pre-existing**
  `test_timer_fires_tick` lifecycle test caught it immediately. Renamed to
  `_on_tick_cb`. Backprop call: this is a generic Python-hygiene bug (case (a),
  my-code), caught by an existing guard — **no new §V invariant** (an invariant
  can't usefully encode "don't shadow methods"). Recorded here instead. Lesson:
  when extending a class with an `_on_*` attribute, grep the class for an
  identically-named method first.
- **No new invariants needed.** The plan's proposed V.NN guards (loop-shell /
  combat-result / autosave / refresher-lifecycle) had **already** landed as
  V.63–V.66 with the T.10 plan. So this build only flipped status + refreshed the
  files cell — exactly the "build only flips §T status" rule, no `/spec` invariant
  churn.
- **V.63 pull toward a shared dispatcher.** The naïve path was to inline the
  `node_type → generate_*` switch in the Trail view. V.63 ("the run loop computes
  no game logic") + the knowledge that Prep (T.23) needs the *same* mapping pushed
  it into `game/encounter.node_encounter`. One seam, deterministic, testable, and
  drift-proof between preview and the real fight. Worth the extra dataclass.
- **Stub seams stay honest.** Play Next lands on a clearly-marked `_push_prep_stub`
  (like T.10's old trail stub) rather than faking Prep — the decoupled
  `on_play_next(node)` callback means T.23 swaps the producer with zero Trail edits.

## Follow-up (same session): UNKNOWN-display fix + Settings menu

User playtest-by-inspection drove two changes right after the core T.11 landed:

1. **"Unloaded weather should show unknown, not default."** The first cut followed
   V.66 literally — UNKNOWN cache entries rendered the city `default_weather`. The
   user (correctly) flagged that painting unfetched weather as if it were live is
   misleading. **Amended V.66** to a **tri-state display contract**: UNKNOWN → a `?`
   "pending" marker (favor `— pending`), SUBSTITUTE → default weather flagged
   `fallback`, LIVE → unflagged. Crucially split **display weather** from
   **game-logic weather** — `node_encounter`/favor still derive from the node's
   `default_weather` deterministically (V.2), so the preview is stable as live data
   streams in; only the *displayed* live value goes tri-state. `route_map`'s
   `weather: WeatherState | None` (None = unknown) keeps the viz free of `CacheState`.

2. **"We don't have a key yet / how do I input it?" → Settings menu.** Two real
   gaps surfaced:
   - **The app never loaded `.env`.** `python-dotenv` is a *dev* dependency and only
     `conftest.py` called `load_dotenv` — so a key in `.env` reached the tests but
     **not** `flet run`. Added a **soft** `load_dotenv` to `main.py` (guarded import,
     no-op in packaged builds without the dev dep; existing env var always wins).
   - **No in-app way to set the key.** Built `src/app_config.py` (Flet-free config
     I/O, atomic save, `resolve_api_key` = env → file → None) + a **Settings view**
     off the menu. Persisted to a user-data `config.json` **sibling of `saves/`** —
     deliberately *not* `game/save.py` (V.36 owns *Run* persistence only). Key masked
     in the field, never logged (V.3). The Trail now resolves the key via
     `app_config` instead of reading the env directly, so a Settings-saved key lights
     up live weather with no terminal.

Both verified visually (Playwright): no-key Trail shows `?` everywhere; menu shows
the new Settings entry; Settings view renders the masked field + status + config
path. Full suite 1401 passing.

**Process note — the stale-frame red herring.** The first post-fix screenshot *still*
showed default weather, which nearly sent me hunting a phantom bug. Cause: Flutter
web's **service worker** served a cached frame from the prior session. Re-screenshot
with `service_workers="block"` + a longer settle showed the correct `?` state. Lesson
for this project's UI self-verify loop: **block the service worker** (or hard-reload)
when re-shooting the same app across code changes, or you'll review stale pixels.

## Follow-up 2 (same session): the refresher actually painting the view

User, on the **desktop** app with all nodes `?`: "staying on the Trail should update as
new weather comes in — refresh on scheduler return (3 nodes/pulse)." Three real defects
behind that one symptom:

1. **No fetch on open.** The refresher's first `threading.Timer` tick is a full
   `tick_interval` (~60s) out — so for the first minute the Trail showed nothing even
   with a valid key. Added a **kickstart worker thread** on open: fetch the *current*
   node immediately (`fetch_and_cache`, the T.7-sanctioned sync fetch, off the main
   thread per V.4), then one seed `refresher.tick()` for neighbours.
2. **Worker-thread `page.update()` is unreliable on desktop.** The repaint path was
   `on_tick → _render → page.update()` *on the Timer thread*. It worked in the web
   renderer (my earlier screenshots) but not reliably in the desktop client — and the
   refresher **swallows** `on_tick` exceptions (logs only), so a failed repaint was
   invisible. Fix: `_schedule_render` marshals onto the Flet event loop via
   **`page.run_task`** (`asyncio.run_coroutine_threadsafe` under the hood) — exactly
   the pattern `combat.py` autoplay already uses (`page.run_task(_autoplay_loop)`). I'd
   *had* the proven pattern in-repo the whole time and not matched it; reading the
   neighbour view's threading model first would have saved a round-trip.
3. **Silent no-key state.** All `?` with no explanation reads as "broken," not "needs a
   key." Added a no-key banner pointing at Settings.

Verified the marshaled repaint via a stubbed `WeatherClient.fetch_weather` harness:
current node + a neighbour populate live on open through `page.run_task`, proving the
same path the 60s pulses take.

**Process note — web ≠ desktop for thread-safety.** My self-verify loop screenshots the
**web** build (`flet run --web` + Playwright), but the user runs **desktop**. A
`page.update()` from a background thread that *renders fine in web* silently no-ops on
desktop. The screenshot gate is necessary but not sufficient for threading behaviour —
when a fix involves a non-main thread touching the UI, match the codebase's proven
marshaling pattern rather than trusting the web screenshot.

## Prompting-strategy reflection

- The single most leveraged move was **front-loading the required reading in
  parallel** (SPEC §V + plan doc + Node/Run models + cache/refresher + theme +
  dev-harness reference) before writing a line. The plan doc was rich enough that
  the build was mostly transcription — the forks were already resolved. This is the
  SDD payoff: a good plan turns the build into low-entropy work.
- **Smoke-testing each layer as it landed** (route helper → encounter dispatcher →
  viz builder → headless view construction) localized failures to one file at a
  time, so the only real bug (the name collision) surfaced against a tiny diff.
- **Visual verification is not optional for graded Canvas work.** The pure
  `route_node_specs` test proves the data; only the screenshot proves the *pixels*
  (z-order of label-over-circle, scroll container, ring overlays). Cheap insurance
  given the playwright tooling was already wired from the combat-view work.
